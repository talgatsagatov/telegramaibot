# Архитектура проекта

Этот документ описывает **внутреннее устройство** AI RIZQ Bot: модули, их зоны ответственности, потоки данных и схему БД. Если вам нужна инструкция по установке — смотрите [README.md](README.md).

---

## 1. Принципы проектирования

1. **Модульность по бизнес-функциям**, а не по технологиям. У нас не «папка со всеми хэндлерами», а отдельные модули `start`, `ai_dialog`, `lead_form`, `admin` — каждый отвечает за свой сценарий.
2. **Тонкие хэндлеры, толстые сервисы.** Логика OpenAI, rate-limit и БД лежит в `services/` и `database/`. Хэндлеры — это «клей» между Telegram и бизнес-логикой.
3. **Конфиг — единая точка правды.** Все секреты и настройки читаются один раз в `app/config.py` через pydantic-settings. Остальные модули импортируют готовый `settings`.
4. **Тексты — отдельно от логики.** Все user-facing строки в `app/utils/texts.py`. Это упрощает ревью и подготовку к локализации.
5. **Async везде, где возможно.** aiogram, SQLAlchemy, OpenAI SDK и SQLite-драйвер работают в общем event loop без блокировок.

## 2. Карта модулей

```
                ┌──────────────┐
                │   main.py    │  точка входа: bot, dispatcher, polling
                └──────┬───────┘
         ┌─────────────┼──────────────────┐
         ▼             ▼                  ▼
   ┌──────────┐  ┌────────────┐    ┌─────────────┐
   │ handlers/│  │ services/  │    │  database/  │
   │ (тонкие) │──▶ openai     │    │   engine    │
   │          │  │ rate_limit │◀──▶│   models    │
   │          │  └────────────┘    │   crud      │
   └────┬─────┘                    └─────────────┘
        ▼
   ┌──────────┐  ┌──────────┐  ┌──────────┐
   │keyboards/│  │ states/  │  │  utils/  │
   └──────────┘  └──────────┘  └──────────┘
```

### Назначение пакетов

| Пакет | Ответственность | Что **не** делает |
|---|---|---|
| `app/handlers/` | Принимает события Telegram, управляет FSM, отправляет ответы | Не делает HTTP-запросы напрямую, не пишет SQL |
| `app/services/` | Внешние интеграции и бизнес-правила (rate-limit, OpenAI) | Не знает про aiogram и Telegram |
| `app/database/` | Соединение с БД, модели, CRUD | Не содержит бизнес-правил |
| `app/keyboards/` | Конструкторы клавиатур и константы `callback_data` | Не отправляет сообщения |
| `app/states/` | FSM-состояния (StatesGroup) | Не содержит логики переходов |
| `app/utils/` | Валидаторы и тексты | Без зависимости на aiogram/SQLAlchemy |

## 3. Поток управления событиями

```
Telegram update
      │
      ▼
┌──────────────────┐
│   Dispatcher     │   aiogram.Dispatcher (in main.py)
└────────┬─────────┘
         │ роутится по фильтрам и состоянию FSM
         ▼
┌─────────────────────────────────────────┐
│  Routers (в порядке приоритета):        │
│   1. start_router       — /start, /cancel│
│   2. ai_dialog_router   — AIDialog.*    │
│   3. lead_form_router   — LeadForm.*    │
│   4. admin_router       — lead_status:* │
└──────────────┬──────────────────────────┘
               ▼
       Handler-функция
               │
   ┌───────────┼─────────────┐
   ▼           ▼             ▼
services/   database/    keyboards/
   │           │             │
   └───────────┴─────────────┘
               ▼
        bot.send_message
```

Порядок роутеров критичен: `start_router` первый, чтобы команды `/start` и `/cancel` имели приоритет над FSM-обработчиками и работали в любом состоянии.

## 4. Сценарий «Задать вопрос ИИ»

```
Пользователь                 Бот                         OpenAI         БД
     │                         │                            │             │
     │  /start                 │                            │             │
     │────────────────────────▶│                            │             │
     │                         │ greeting + main menu       │             │
     │◀────────────────────────│                            │             │
     │                         │                            │             │
     │  click "Задать вопрос ИИ"                            │             │
     │────────────────────────▶│                            │             │
     │                         │ set_state(waiting_for_question)          │
     │                         │ history := []              │             │
     │                         │ "Напишите вопрос..."       │             │
     │◀────────────────────────│                            │             │
     │                         │                            │             │
     │  "как настроить таргет?"│                            │             │
     │────────────────────────▶│                            │             │
     │                         │  is_allowed(user_id)?      │             │
     │                         │───────────────────────────────────────▶ │
     │                         │◀──── true ──────────────────────────────│
     │                         │ "🤔 Думаю..."              │             │
     │◀────────────────────────│                            │             │
     │                         │  ask([sys_prompt, ...history, user])    │
     │                         │───────────────────────────▶│             │
     │                         │◀──── ответ ───────────────│             │
     │                         │  history += [user, assistant]           │
     │                         │  history := history[-10:] (5 пар)       │
     │                         │  register_successful_request(user_id)   │
     │                         │───────────────────────────────────────▶ │
     │                         │ delete "Думаю..." +        │             │
     │                         │ ответ + кнопка "В меню"    │             │
     │◀────────────────────────│                            │             │
```

**Контекст диалога:** хранится в FSM-памяти (`MemoryStorage`) как список объектов `{role, content}`. После каждого успешного ответа история обрезается до последних 10 сообщений (5 пар). При выходе в меню или `/cancel` FSM очищается — история теряется (ожидаемое поведение).

**Rate-limit:** проверка `is_allowed` идёт *до* запроса в OpenAI, инкремент `register_successful_request` — *после* успешного ответа. Если OpenAI ответил ошибкой, счётчик не двигается.

## 5. Сценарий «Оставить заявку» (FSM)

```
                        ┌───────────────────────┐
                        │  click "Оставить       │
                        │  заявку" → start FSM   │
                        └────────────┬───────────┘
                                     ▼
                          LeadForm.waiting_name
                          ┌──────────┴──────────┐
                          │  validate_name()     │
                          └──────────┬──────────┘
                                     │ ok
                                     ▼
                          LeadForm.waiting_phone
                          ┌──────────┴──────────────┐
                          │ contact OR text         │
                          │  → validate_phone()     │
                          │  → normalize_phone()    │
                          └──────────┬──────────────┘
                                     │ ok
                                     ▼
                       LeadForm.waiting_description
                          ┌──────────┴──────────────┐
                          │  validate_description() │
                          └──────────┬──────────────┘
                                     │ ok
                                     ▼
                          LeadForm.confirmation
                          ┌──────────┴──────────────┐
                          │  показ сводки + buttons │
                          │  Confirm / Back / Cancel│
                          └──────────┬──────────────┘
                                     │ Confirm
                                     ▼
                          ┌──────────────────────┐
                          │  create_lead(...)    │  ──▶ INSERT INTO leads
                          └──────────┬───────────┘
                                     ▼
                          ┌──────────────────────┐
                          │ send_new_lead_       │  ──▶ admin chat
                          │ notification(bot, l) │
                          └──────────┬───────────┘
                                     ▼
                              clear FSM,
                            показ "Заявка #N
                              отправлена"
```

**Параллельные пути:**
* На любом шаге доступна команда `/cancel` (через `start_router`) — мгновенный выход в меню.
* На каждом шаге, кроме первого, есть кнопка «← Назад», возвращающая в предыдущее состояние без потери уже введённых данных.
* На шаге «Телефон» работают **два** обработчика: один для `message.contact` (нажата кнопка), второй для `message.text` (введено вручную). aiogram сам разруливает по фильтрам `F.contact` / `F.text`.

## 6. Сценарий «Админ обрабатывает заявку»

```
Lead создан → send_new_lead_notification(bot, lead)
                       │
                       ▼
            bot.send_message(ADMIN_CHAT_ID,
                             text=summary,
                             reply_markup=admin_lead_kb(lead.id))
                       │
                       ▼
           Админ видит карточку:
           ┌─────────────────────────────────┐
           │ 🔔 Новая заявка #42             │
           │ 👤 Имя: Иван                    │
           │ 📱 Телефон: +79991234567        │
           │ 📝 Проект: ...                  │
           │ 🕐 02.05.2026 14:23 UTC         │
           │ ─────────────────────────────── │
           │ [🟢 Взять в работу] [🔴 Закрыть] │
           └─────────────────────────────────┘
                       │
                       │  click button
                       ▼
           callback_data: "lead_status:in_progress:42"
                       │
                       ▼
            ┌──────────────────────┐
            │ user_id == ADMIN?    │
            └──────┬───────┬───────┘
                   │ нет   │ да
                   ▼       ▼
              alert      update_lead_status(session, 42, IN_PROGRESS)
              "только                │
              админу"                ▼
                          edit_text(text + "\n\nСтатус: 🟢 В работе",
                                    reply_markup=None)
```

Защита от посторонних: `process_lead_status` сравнивает `callback.from_user.id` с `settings.admin_chat_id`. Если не совпадает — alert и выход без изменений в БД.

## 7. Схема базы данных

```
┌─────────────────────────────────────┐    ┌─────────────────────────────────────┐
│            leads                    │    │          usage_limits               │
├─────────────────────────────────────┤    ├─────────────────────────────────────┤
│ id              INTEGER PK          │    │ id                INTEGER PK        │
│ tg_user_id      BIGINT (indexed)    │    │ tg_user_id        BIGINT UNIQUE     │
│ name            VARCHAR(50)         │    │ requests_count    INTEGER           │
│ phone           VARCHAR(20)         │    │ window_started_at DATETIME (UTC)    │
│ description     TEXT                │    │                                     │
│ status          VARCHAR(20)         │    │  Логика: окно 24 часа,              │
│   ENUM('new',                       │    │  при истечении сбрасывается         │
│        'in_progress',               │    │  на 1 + текущее время.              │
│        'closed')                    │    │  Лимит: requests_count < 10.        │
│ created_at      DATETIME (UTC)      │    │                                     │
│ updated_at      DATETIME (UTC)      │    │                                     │
└─────────────────────────────────────┘    └─────────────────────────────────────┘
```

Связь между таблицами не нужна: `usage_limits.tg_user_id` совпадает с `leads.tg_user_id`, но разные пользователи могут оставлять заявки и не задавать вопросы ИИ (и наоборот). Объединять их в одну таблицу было бы преждевременной нормализацией.

**Почему `Enum(native_enum=False)`:** SQLite не поддерживает нативный тип `ENUM`. SQLAlchemy сохраняет статус как `VARCHAR(20)` и валидирует значения на уровне приложения.

**Почему `tg_user_id` это BIGINT:** Telegram user_id может превышать 2^31 (для новых пользователей это уже норма), поэтому INT недостаточно.

## 9. FSM-хранилище

В проекте используется `MemoryStorage` из aiogram — данные FSM (текущее состояние и история диалога с ИИ) хранятся в RAM процесса. **Последствия:**

* После рестарта бота все активные сессии диалога с ИИ теряются.
* Незавершённые формы заявки тоже сбрасываются.

Для production-проекта стоит перейти на `RedisStorage` — это меняет одну строку в `main.py`. Для текущих задач `MemoryStorage` достаточно.

## 10. Точки расширения

Если в будущем понадобится развивать проект — вот основные точки:

| Хочется добавить... | Куда смотреть |
|---|---|
| Новый сценарий (например, FAQ) | Новый модуль в `app/handlers/`, новый `Router`, регистрация в `main.py` |
| Новые состояния FSM | Добавить в `app/states/fsm_states.py` |
| Новые callback-кнопки | Константа `CB_*` в `app/keyboards/inline.py` + новый builder |
| Новая таблица БД | Модель в `app/database/models.py`, CRUD в `app/database/crud.py` |
| Локализация (английский, например) | `app/utils/texts.py` → словарь `{lang: {...}}` + middleware определения языка |
| Сохранение истории диалога с ИИ между сессиями | Перейти на `RedisStorage` или новая таблица `ai_messages` в БД |
| Веб-админка для заявок | Отдельный сервис (FastAPI), читающий из той же `bot.db` |
